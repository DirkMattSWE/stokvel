# Stokvel Prototype — Build Spec

Single-stokvel MVP. **Spring Boot (Java) + React + STOMP over WebSocket + SQLite**
(MySQL fallback if the Hibernate dialect setup costs too much of the build window).

The evaluation is on approach and reasoning, not stack choice or feature count.
Code should be thin and explainable over clever.

**Ponytail is active in this session.** Its bias toward fewer abstractions and less
code is correct almost everywhere in this codebase — but the `Payment`/`Allocation`
split below is deliberate indirection, not accidental complexity. It exists so Rule 7
(debt-settles-first) is a logic change instead of a schema rewrite. Do not collapse
`Payment` and `Allocation` into one table or one class for the sake of fewer lines.
Same holds for `Debt` having no `status` column, and for `Payment.payout_id` existing
as an explicit nullable FK rather than being inferred from timing — both are there to
avoid a second source of truth, not because nobody thought to simplify them.

---

## The one principle everything follows

**Every fact is appended. Nothing is overwritten. Totals are derived.**

Smell test — if you write `pot += amount` or `member.debt -= amount`, the model has
been violated. Same test one level up: if a column or entity exists only to cache a
fact you could query from other rows, it should not exist.

Ask: *"is this a new fact, or the answer to a question I could ask the existing tables?"*

The single mutable value in the entire system is `stokvel_config.current_date`, and
only because it cannot be derived from anything else.

## Schema

### `stokvel_config`
Singleton row (`id = 1`). No foreign keys in or out.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK | Always 1 |
| `contribution_amount` | DECIMAL | Fixed, per member per cycle |
| `current_date` | DATE | The system's notion of "today" (Rule 8) |

### `member`

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK | |
| `name` | TEXT | |
| `created_at` | TIMESTAMP | Implies rotation position (Rule 5) |

No stored `position` — rotation order *is* creation order, never reordered.
No `debt` column. No `is_active` — Rule 3's mid-cycle exclusion derives from
`created_at` vs the cycle's `due_date`.

### `cycle`
One row per round.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK | |
| `sequence_number` | INTEGER | Round 1..N |
| `due_date` | DATE | What the clock compares against |
| `recipient_id` | INTEGER FK → member | Fixed at cycle creation |

No start date — a cycle's start is the previous cycle's due date. The rotation as a
whole is `MIN`/`MAX`/`COUNT` over these rows, never a separate entity.

`sequence_number` is derivable from date order but kept deliberately: cycles are never
reordered or deleted, so it has **no drift path**, and it makes every query and UI
label readable. This is the one deliberate exception to the derive-everything rule.

### `payment`
The raw fact that money arrived.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK | |
| `member_id` | INTEGER FK → member | |
| `amount` | DECIMAL | |
| `payout_id` | INTEGER FK → payout, **nullable** | Set when auto-generated by an arrears deduction |
| `created_at` | TIMESTAMP | |

**No `cycle_id`.** Which cycle a payment counts toward is the *allocation's* job. That
separation is what makes Rule 7 a logic change rather than a rewrite.

`payout_id` marks a payment as system-generated rather than voluntary — an explicit
link, never inferred from timing.

### `allocation`
Where a slice of a payment landed.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK | |
| `payment_id` | INTEGER FK → payment, NOT NULL | |
| `cycle_id` | INTEGER FK → cycle, **nullable** | |
| `debt_id` | INTEGER FK → debt, **nullable** | |
| `amount` | DECIMAL | |

**Exactly one of `cycle_id` / `debt_id` must be set.** Enforce in the service layer;
a CHECK constraint is optional belt-and-braces.

An allocation is a *slice* of one payment, not a monthly total. One payment produces
one row per destination. Buy-ins deliberately do **not** allocate here — a third
destination type would push this into polymorphic-FK territory, which SQLite cannot
enforce and JPA fights.

### `debt`
Immutable record of a shortfall.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK | |
| `debtor_id` | INTEGER FK → member | Who failed to pay |
| `creditor_id` | INTEGER FK → member | Who was under-paid |
| `cycle_id` | INTEGER FK → cycle | Which round caused it |
| `amount` | DECIMAL | **Never decremented** |
| `created_at` | TIMESTAMP | Drives oldest-first settlement |

Two FKs to the same table — an ordinary entity with two roles, not a junction table.
One member appears in many rows, in either column.

**No `status`, no `amount_remaining`, no `is_settled`.** A flag can disagree with the
allocation rows; the subtraction cannot, and it handles partial settlement for free.

### `payout`
A single event, not a range — the range belongs to the cycle.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK | |
| `cycle_id` | INTEGER FK → cycle | |
| `recipient_id` | INTEGER FK → member | |
| `amount_paid` | DECIMAL | **Gross** — before arrears deduction |
| `created_at` | TIMESTAMP | |

Nothing allocates *to* a payout. Money flows out, not in.

### `buyin` and `buyin_distribution` — build last

`buyin`: `id`, `member_id` (the joiner), `amount`, `created_at`

`buyin_distribution`: `id`, `buyin_id`, `recipient_id` (an already-paid member), `amount`

Same event-then-distribution shape as payment/allocation. Needed because one buy-in
splits across several already-paid members proportionally to their gap (Rule 4) — a
single amount on a single row cannot express that.

### Explicitly not tables

- **Ledger** — a view over existing rows in timestamp order. A table would be a second
  source of truth needing sync.
- **Rotation** — `MIN`/`MAX`/`COUNT` over cycle rows.
- **Stokvel** as a relational parent — single deployment, so config is a singleton row
  with no relationships.

## Derived, never stored

| Question | How |
|---|---|
| Pot for a cycle | `SUM(allocation.amount) WHERE cycle_id = ?` |
| Target pot | `contribution_amount × COUNT(member)` |
| Outstanding on one debt | `debt.amount − SUM(allocation.amount WHERE debt_id = ?)` |
| A member's total arrears | Sum of the above across their debtor rows |
| Current cycle | Earliest cycle with `due_date ≥ current_date`, or earliest with no payout row |
| Rotation length | `COUNT(member)` — equals `COUNT(cycle)` |
| Who is behind | Expected vs actual allocations, per member per cycle |
| Net received at payout | `payout.amount_paid − SUM(allocations from payments WHERE payout_id = ?)` |
| The ledger | Union of payment / allocation / debt / payout / buyin rows in timestamp order |

## Business rules

**Rule 1 — payout fires on the due date, regardless.** Pays whatever is actually in the
pot, not the target. No delay, no waiting, no judgment call. The clock compares
`current_date` against `cycle.due_date`; nothing else triggers a payout.

**Rule 2 — shortfall becomes tracked debt.** One debt row per non-payer, naming the
under-paid recipient as creditor — not "the group" in the abstract. Appended, never
mutated. Visible on the ledger indefinitely.

**Rule 3 — late join goes to the back of the rotation.** Mid-cycle joiners are excluded
from the in-progress cycle and become liable from the next one. No proration.

**Rule 4 — buy-in fully compensates already-paid members.** The joiner pays the full gap;
top-ups distribute immediately to affected members, not accrued as credit. Buy-in money
does **not** enter the current pot.

**Rule 5 — rotation order fixed at creation.** `member.created_at` is the order.
`cycle.recipient_id` is set once, at cycle creation. Never reordered.

**Rule 6 — arrears never block a payout.** The member still receives their turn; their
outstanding debt is deducted from what they receive. `payout = max(0, pot - outstanding_debt)`
— write the floor defensively even though Rule 9 makes it structurally unreachable.

Mechanically: the payout row records **gross**. The deduction is a real `payment` row
with `payout_id` set, whose allocations settle the debts. This keeps `allocation`
uniform — every allocation has a payment, no nullable `payment_id`, one code path.
The ledger then shows both lines, which is better for transparency than a single net
number:

```
PAYOUT   John receives          R1,000
PAYMENT  John — auto-deducted   −R200   (settles debt to Sarah, Thabo)
                                ───────
                                  R800
```

**Rule 7 — debt settles first, oldest first.** A payment's allocations clear outstanding
debts in `created_at` order; the remainder flows to the current cycle's pot. Only the
allocation logic changes — pot and ledger queries are untouched because the pot was
always derived from allocations, never from raw payments.

*Standing risk, deliberately visible:* a member paid out early can accrue debt with no
future payout to deduct from. The software cannot compel repayment and should not
pretend to. The debt sits on the ledger indefinitely — visibility is the enforcement
mechanism.

**Rule 8 — the clock.** Business logic **never** reads system time. No `LocalDate.now()`
in any rule. `current_date` lives in the DB (a restart mid-demo must not reset it).
Cycle boundary is end of month. An advance function moves the date, then asks the system
what has become due — **it does not pay anyone out.** The payout fires on its own because
the date is due. Same code path in production, just driven by real time.

**Rule 9 — rotation length = member count.** Derived, not hard-coded. Single rotation for
MVP. This bound is what guarantees a member's maximum debt cannot exceed one pot, which
is why the `max(0, …)` floor never fires in practice.

## Architecture

**Service layer separate from transport.** Business logic lives in plain callable
services — `recordPayment()`, `advanceClock()`, `checkDue()`, `getArrears()`,
`getLedger()`. Controllers call services. Services own the rules. Nothing
business-critical lives in a controller or a React component.

**Append-only means no update or delete paths.** `recordPayment()` exists;
`updatePayment()` and `deletePayment()` must not. If no edit endpoint exists, there is
structurally nothing to tamper with.

**Real-time.** Server owns state. On any ledger write, broadcast to `/topic/ledger` via
STOMP. Clients subscribe once and re-render from pushed state — they do not poll and do
not recompute authoritative values locally.

---

## Build order

1. **Spine, end to end, ugly:** create members + config → record payments → allocations
   to the current cycle's pot → clock advance → payout fires on due date → ledger view
2. Debt tracking and display (Rule 2, Rule 6 deduction)
3. Rule 7 debt-first allocation
4. Buy-in redistribution
5. Polish — legible from the back of the room

If buy-in does not make the build, it is presented as a specified-and-scoped rule.

## Out of scope

Auth, mobile responsiveness, real money/EFT/payment gateways, email/SMS/push,
background scheduler (the clock control does that job).
