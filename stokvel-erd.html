Entities

stokvel_config
ColumnTypeNotes
idINTEGERPK — always 1
contribution_amountDECIMALFixed per member per cycle
current_dateDATEThe system's notion of "today" (Rule 8)

Singleton row. No foreign keys in or out — its isolation in the diagram is the proof it is config, not a relational parent. The only mutable value in the entire schema is current_date, and only because it cannot be derived from anything else.

member
ColumnTypeNotes
idINTEGERPK
nameTEXT
created_atTIMESTAMPImplies rotation position (Rule 5)

No stored position — rotation order is creation order, never reordered. No debt column — outstanding debt is a query. No is_active — Rule 3's mid-cycle exclusion derives from created_at vs the cycle's due_date.

cycle
ColumnTypeNotes
idINTEGERPK
sequence_numberINTEGERRound 1..N — human-readable identity
due_dateDATEWhat the clock compares against
recipient_idINTEGERFK → member, fixed at creation

One row per round. No start date — a cycle's start is the previous cycle's due date. The rotation as a whole is MIN/MAX/COUNT over these rows, not a separate entity. sequence_number is technically derivable from date order, but cycles are never reordered or deleted, so it has no drift path — kept for query and UI readability.

payment
ColumnTypeNotes
idINTEGERPK
member_idINTEGERFK → member
amountDECIMALRaw fact: money arrived
payout_idINTEGERFK → payout, nullable — set when auto-generated by an arrears deduction
created_atTIMESTAMP

No cycle_id — which cycle a payment counts toward is the allocation's job, not the payment's. That separation is what makes Rule 7 a logic change rather than a rewrite. payout_id marks a payment as system-generated rather than voluntary — an explicit link, never inferred from timing.

allocation
ColumnTypeNotes
idINTEGERPK
payment_idINTEGERFK → payment, NOT NULL
cycle_idINTEGERFK → cycle, nullable
debt_idINTEGERFK → debt, nullable
amountDECIMALThis slice of the payment

Exactly one of cycle_id / debt_id must be set. Enforced in the service layer (a CHECK constraint is optional belt-and-braces). An allocation is a slice of a payment, not a monthly total — one payment produces one row per destination. Buy-ins deliberately do not allocate here; a third destination type would push this into polymorphic-FK territory.

debt
ColumnTypeNotes
idINTEGERPK
debtor_idINTEGERFK → member — who failed to pay
creditor_idINTEGERFK → member — who was under-paid
cycle_idINTEGERFK → cycle — which round caused it
amountDECIMALImmutable. Never decremented.
created_atTIMESTAMPDrives oldest-first settlement order

Two foreign keys to the same table — this is an ordinary entity with two roles, not a junction table. No status column, no amount_remaining. A flag can disagree with the allocation rows; the subtraction cannot, and it handles partial settlement for free. One member can appear in many rows, in either column.

payout
ColumnTypeNotes
idINTEGERPK
cycle_idINTEGERFK → cycle
recipient_idINTEGERFK → member
amount_paidDECIMALGross — before arrears deduction
created_atTIMESTAMP

A single event, not a date range — the range belongs to the cycle. Nothing allocates to a payout; money flows out, not in. Net received is derived, not stored (see below).

Same event-then-distribution shape as payment/allocation. Needed because one buy-in splits across several already-paid members proportionally to their gap (Rule 4) — a single amount on a single row cannot express that.

Rules the schema encodes

Rule 1 — payout fires on the due date The clock compares stokvel_config.current_date against cycle.due_date. Nothing else triggers a payout.
Rule 2 — shortfall becomes tracked debt One debt row per non-payer, naming the under-paid recipient as creditor. Appended, never mutated.
Rule 5 — rotation order fixed at creation member.created_at is the order. cycle.recipient_id is set once, at cycle creation.
Rule 6 — arrears deducted, payout never blocked Payout records gross. The deduction is a real payment row with payout_id set, whose allocations settle the debts. Keeps allocation uniform: every allocation has a payment.
Rule 7 — debt settles first, oldest first A payment's allocations clear outstanding debts in created_at order, remainder flows to the current cycle's pot. Only the allocation logic changes; pot and ledger queries are untouched.
Rule 7 — standing risk, deliberately visible A member paid out early can accrue debt with no future payout to deduct from. The software cannot compel repayment. The debt sits on the ledger indefinitely — visibility is the enforcement mechanism, not a mechanism the schema pretends to have.

Explicitly not tables

  • Ledger — a view over existing rows in timestamp order. A table would be a second source of truth needing sync.
  • Rotation — MIN/MAX/COUNT over cycle rows.
  • Stokvel (as a relational parent) — single deployment, so config is a singleton row with no relationships.

The smell test

If you write pot += amount or member.debt -= amount, the model has been violated. Same test one level up: if an entity or column exists only to cache a fact you could query from other rows, it should not exist. Ask "is this a new fact, or the answer to a question I could ask the existing tables?"

The one deliberate exception is cycle.sequence_number — derivable in principle, but cycle rows are never reordered or deleted, so it has no drift path.
